# PLAN: AI Catalog specVersion 1.0: format crate, client, front ends, Lambda handler and trust crate
Upstream as fetched: spec last commit 2026-11-10; ai-catalog-rust version 0.4.0.
Approved: 2026-11-17 (maintainer: "approved, start implementing")

Scope: the workspace `turul-agent-card` (M1) holding six crates: `turul-ai-catalog` (format: model, parse, validate, serialise, resolution rules; sync, no I/O, zero runtime deps; never decodes JWS or base64url, M12), `turul-ai-catalog-client` (consumer: file and HTTPS loading under Safe Fetching, well-known lookup, nested traversal, diagnostics, filtering), `turul-ai-catalog-tui` and `turul-ai-catalog-cli` (thin front ends over the client), `turul-ai-catalog-lambda` (serves one bundled catalog) and `turul-ai-catalog-trust` (signed payloads, artifact digests, ES256 signing, JWS protected-header policy, `did:web` signer shape and `did-web-v1` verification, all JWS work through `turul-jwt-validator`). Spec anchors refer to `target/upstream/ai-catalog/specification/ai-catalog.md`. Crate-relative test paths are under `crates/<crate>/tests/`.

## 2. Crate layout and dependency direction

```
turul-a2a / turul-mcp-framework / turul-agent-skills   (consumers; never edited here)
        │
        ▼
turul-ai-catalog          format; no runtime deps (M6); dev: ai-catalog-rust (M4, D15), sha2 (D17)
        ▲            ▲
        │            └── turul-ai-catalog-lambda   lambda_http, tokio; dev: client, ai-catalog
turul-ai-catalog-client   reqwest (blocking, rustls), url; dev: sha2 (D17)
        ▲            ▲
        │            └── turul-ai-catalog-trust    sha2, turul-jwt-validator (M10, M14); dev: ai-catalog-trust
turul-ai-catalog-tui      ratatui, crossterm
        ▲
turul-ai-catalog-cli      clap; binary `turul-ai-catalog` (`ai-catalog` is the official CLI's name)
```

Rules:
- The format crate has no network, async or crypto dependency, and no A2A, MCP or skills type appears anywhere. It never decodes JWS or base64url (M12): no `jws` or `base64url` module and no base64 alphabet literal in its `src/` (trust `tests/crypto_boundary.rs` scans it), so the validator holds turul's one decoder.
- The network dependency lives only in the client. Loading a local file needs no network. The trust crate fetches only through `turul_ai_catalog_client::fetch`.
- Only the trust crate depends on `turul-jwt-validator` or (at runtime) `sha2`. It has no direct `p256`, `jsonwebtoken`, `base64`, `ring`, `aws-lc-rs` or `serde_json` dependency and no `std::net` in `src/`. The validator's resolved features are `detached_rust_crypto` and what it implies, never `jwks` (a depth-1 tree cannot show this, and `tokio` already arrives through the client's blocking `reqwest`). Trust `src/` holds no base64 alphabet literal and no `split('.')`/`split(".")`; JWS text reaches only `turul_jwt_validator::detached`'s `inspect_detached`, `verify_detached` and `sign_detached_es256` (trust `tests/crypto_boundary.rs`). The header map `inspect_detached` returns is read for `kid` through inherent methods only, so no `serde_json` type is named. Trade-off: a signing-only consumer still builds the client's `reqwest`; no feature gate, because nothing needs one today.
- `client::fetch`, `load`, `did_web::resolve` and trust `verify` are blocking (`reqwest::blocking`, D15), which panics on a tokio runtime thread. Async consumers call them through `tokio::task::spawn_blocking`; each carries a rustdoc note (ADR-008, ADR-015). No async variant is built: no consumer needs one today.
- The TUI and CLI depend only on the crates shown (never on the trust crate); `tests/dependency_direction.rs` (CLI crate) fails on any other direct dependency, or on `std::net` or `std::fs` in their `src/`.
- All dependencies use `workspace = true`.
- Public enums and error types are `#[non_exhaustive]`; error types implement `std::error::Error` and `Display`. Model structs are `#[non_exhaustive]`, with public fields whose identity values are typed keys, and a `new(required members…)` constructor.

## 5. Ordered slices

Gates for every slice:
1. `cargo fmt --all -- --check`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `cargo test --workspace`
4. `RUSTDOCFLAGS=-D warnings cargo doc --no-deps --workspace`

6. The `adr-review` subagent with no BLOCKER or HIGH findings

Every slice bumps the patch version and updates `CHANGELOG.md`.

Stop conditions for every slice:
- An unanswered ask that the slice depends on (none open).
- A test that disagrees with the spec (re-read the spec and escalate; the test is not changed to fit the code).
- A dependency not named in §0b (M6, D15 and its M9/M10 additions).
- A gate failure after 3 attempts.
- Any write outside this repository.
- T2, S14, T3, T4: the `turul-jwt-validator` detached-JWS API (`inspect_detached`, `verify_detached`, `sign_detached_es256`, `check_public_jwk`) is unreleased (0.3.4 not published), or it needs an input type (for example `serde_json::Value`) the trust crate cannot build from `Json` canonical bytes without a new dependency, or a return type the trust crate must name (the `inspect_detached` map is read for `kid` through inherent methods only; the `verify_detached` map is ignored), or a private key in any form other than PKCS#8 DER bytes (ADR-013). Report; never work around it with local crypto or a local decoder (M10, M12).

- AMB-72: display-name step 3 takes the text after the last `:` or `/`. If there is no delimiter, or the segment is empty, the whole identifier is used (resolution).
- AMB-73: a relative `url` resolves against the fetching document's URL (RFC 3986 §5), through the one owner `client::resolve_reference`, for nested catalogs and for artifact retrieval alike; without a base it is unresolvable. Cycle tracking compares resolved URL strings exactly, with no further normalisation (nested_traversal).
- AMB-74: the client accepts `application/ai-catalog+json`, and `application/json` with a `media-type-generic` warning (#link-relation-discovery step 4); anything else is refused (response_acceptance).
- AMB-75: "render it as given" (#catalog-entry) vs "MUST treat it as untrusted input" (#embedded-content-safety): text is shown as given except that `Cc` characters become U+FFFD; the MUST wins over the SHOULD (display_text).
- AMB-76: Safe Fetching leaves limits consumer-defined; `FetchPolicy::default()` uses 4 MiB, 10 s and 5 redirects, documented in ADR-008 (safe_fetching).
- AMB-77: root `did:web` domain (#the-did-web-signer-profile): `did:web:` followed by '.'-separated labels of `[a-z0-9-]`, each 1–63 characters and not starting or ending with `-`, at most 253 characters in total. `xn--` A-labels are accepted as LDH text and not IDNA-validated (M6: no IDNA dependency). Rejected: any non-ASCII character (U-label), uppercase, `%3A` (port), a further `:` (path), a trailing `.`, and any IP-address spelling, defined as the WHATWG URL "ends in a number" rule the client's `url` parser applies: the last label is all digits, or `0x` followed only by hex digits (so `192.0.2.1`, `2130706433`, `127.1` and `0x7f.0.0.1` are rejected; IPv6 needs `[`, which is outside the label alphabet) (did_web_signer, publisher_authorization). Reasoned from the WHATWG host parser, not yet run; S14 runs it.
- AMB-78: `UrnAir::parse` needs the exact, case-sensitive prefix `urn:air:`, then at least three `:`-separated non-empty components: publisher (first), name (last) and namespace (all between). Exact, because publisher authorization forbids normalisation (#the-did-web-publisher-profile). A publisher that fails AMB-77 parses but is never authorised (urn_air, publisher_authorization).
- AMB-79: `kid_matches_signer`: `kid` is exactly the signer, then `#`, then a non-empty RFC 3986 `fragment`. Because the signer is an exact prefix, no path or query can appear (jws_header).
- AMB-80: DID-document responses must be status 200 with media type `application/did+json`, `application/did+ld+json` or `application/json` (DID Core representations); anything else is refused, and the body goes through the one strict reader (did_resolution).
- AMB-81: #safe-fetching restricts fetches to "the `https` scheme (or inline `data:` URIs)", which permits but does not require `data:` retrieval, and #verifying-artifact-integrity step 2 retrieves "bytes from `entry.url`". Decision: an entry `url` with the `data:` scheme is not decoded (decoding standard base64 and percent-encoding would be a new algorithm and the trust crate has no `base64`, §2); `verify_artifact` gives `IntegrityError::Unsupported(DataUri)` without a request, so that entry is never covered. Publishers inline content with the entry's `data` member instead. `client::fetch` itself stays `https` only (artifact_integrity).
- AMB-82: RFC 8259 §8.2 allows unpaired surrogate escapes; I-JSON (RFC 7493 §2.1), required for signed payloads (#signed-payload-and-jws-construction), forbids them, and `Json` strings are Rust `String`s, which cannot hold them. Decision: the one reader refuses any unpaired surrogate escape at parse with `ParseErrorKind::LoneSurrogate` and its pointer, rather than replacing it (which would silently alter the document). Trade-off: an unsigned document with `"\ud800"` is refused although RFC 8259 allows it; serde_json, and so ai-catalog-rust, refuses it too (string_escapes, sdk_interop).
