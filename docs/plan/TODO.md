# Features not yet addressed

Agreed as worth doing, or open questions to settle, but not started. Each one starts with an ADR when the maintainer picks it up.

| Id | Item | Open question | Starts with |
|---|---|---|---|
| F1 | Runtime self-registration of turul services | Do turul-a2a and turul-mcp services add their own entries to the catalog at runtime, through the M19 `CatalogStore`, or is the catalog curated and deployed with the CLI? The store (M19, ADR-016) supports both, but who registers, when, under what authority, and with what removal or expiry is not decided. Covers the spec's #catalog-projection. | An ADR naming the registering services, the authority model, and entry lifecycle (add, refresh, remove). The work in turul-a2a and turul-mcp-framework goes in handoffs to those sessions. ADR: docs/adr/ADR-017-runtime-registration.md (Proposed) |
| F2 | Serve a stored catalog signed as a whole (next year) | How does a catalog assembled from a store carry a catalog signature (#catalog-snapshot-coverage, a SHOULD) that stays valid for the bytes actually served? Today `import` refuses a signed catalog (`ImportError::Signed`) and the Lambda assembles the served document from the stored entries, so the signature must either be stored with the entries or applied at assembly. The signing key must stay out of the serving function; giving its role access to the Parameter Store key needs the operator's approval. | An ADR choosing stored-signature versus sign-at-assembly, how the signature stays bound to the served bytes, and where the key lives. When it ships, the downstream upgrade is dispatched as its own slice. |

Input received (consumers are not named; this library is independent of any one project):
- F1, 2026-11-17, from one downstream consumer: its catalog is curated and deployed with the tooling, with no runtime self-registration. Reasons given: entries change only when a service is added, removed or moved; self-registration would need a start-up write and store permission on every service; and the spec's #catalog-projection needs an authority model the spec does not define. One data point, not a decision.
- F1, 2026-11-17, design input from one downstream operator (views, not decisions). The spec facts were checked against #catalog-projection:
  - Spec (#catalog-projection): "A catalog operator MUST NOT infer publisher authorization" from the artifact's URL or an unsigned publisher field. An assigned identifier "MUST remain stable across" versions, source-coordinate and retrieval-URL changes, and "MUST NOT be reassigned". Operator and publisher are distinct roles. It constrains identity, not mechanism, and neither requires nor forbids runtime registration.
  - Authority: store write access (IAM) is not authority to register an identifier. Suggested minimum: a per-writer allow-list of `urn:air` publisher domains configured by the operator; optionally, a signed Trust Manifest from the publisher, where Level 3 is wanted. Refuse a registration when neither is configured, so "no check" is never the silent default. Non-`urn:air` identifiers are accepted only under an operator-configured prefix.
  - Identity: the registering service presents its identifier and the library never derives one from an address. A re-registration from a new address under the same identifier is an update.
  - Lifecycle: two modes, a lease that expires unless refreshed (self-registration) and persist-until-removed (curated import). Each entry records which mode wrote it, and a write from the other mode is refused. Expiry must never silently drop an entry: assembly reports what it left out and why. Lease refreshes from many instances must be idempotent conditional writes, not counters. The serving cache must not outlive the lease by much.
  - Demand: curated-and-deployed is expected to be the norm where an operator owns and deliberately deploys every listed service. Self-registration earns its cost for many short-lived services, platforms hosting others' agents, or per-tenant agents created at runtime.
- F2, 2026-11-19, from one downstream operator: a catalog served from a store is Level 3 through per-entry publisher manifests, but strict verify reports its catalog signature as "signature unsigned". Wanted next year; no work now.
