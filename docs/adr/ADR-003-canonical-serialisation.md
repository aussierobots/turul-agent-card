# ADR-003: Deterministic serialisation (RFC 8785 JCS) and the I-JSON number rule

- **Status:** Accepted (2026-11-17): every test file below exists and passes, `canonical::write_canonical` is the only JSON writer in the workspace (no `serde_json` in any crate's `src/` or dependencies), and AMB-94 is decided by M20.
- **Date:** 2026-11-17
- **Implements:** under `crates/turul-ai-catalog/tests/`: `canonical_serialisation.rs`, `i_json_numbers.rs`, `i_json_strings.rs`, `schema_digest.rs` (with the owner `support/schema_digest.rs`). Laws this ADR owns are also pinned in `spec_examples.rs` (ADR-001, round-trip half), `unrecognized_members.rs` (ADR-002, serialise half) and `sdk_interop.rs` (ADR-001, law 4 and number agreement).
- **Depends on:** ADR-002 (`json::read`, `Json`, `Number` equality by exact decimal value AMB-88, the model, `parse`), ADR-001 (corpus). Binding decisions: D4 (JCS is the only serialisation), D17 (golden bytes from an independent producer, schema digest), D5 / D15 (dev-dependency `sha2`), M6 (zero runtime dependencies), M20 (the writer is exactly RFC 8785; AMB-94).
- **Spec:** https://ai-catalog.io, `specification/ai-catalog.md` as read in ADR-001 (last commit 2026-11-10). RFC 8785 (JCS), RFC 7493 (I-JSON), RFC 8259.

## Context

D4 makes RFC 8785 JCS the one serialisation of this workspace: documents, `Json` values, the client's JSON output (ADR-009) and signed payloads (ADR-013). The spec requires JCS in two places: the signed payload (#signed-payload-and-jws-construction: "Canonicalize this payload with JCS [[RFC8785]]. Its UTF-8 bytes are the JWS payload. The payload MUST satisfy JCS's I-JSON constraints") and the digest of inline `data` (#catalog-entry `digest`: "For `data`, hash the UTF-8 JCS-canonicalized [[RFC8785]] JSON value. Inline `data` MUST satisfy JCS's input requirements for artifact verification to succeed"). It also requires forwarding to keep `contributor` exactly (#contributor-identity) and asks re-serialisation to keep unrecognised members (#consumer-requirements).

ADR-002's `Number` keeps its source lexeme and compares by exact decimal value. JCS parses every number to its nearest IEEE 754 double and writes that double's ECMAScript form (RFC 8785 §3.1, §3.2.2.3), so where the two disagree JCS changes the decimal value. The spec requires the signed payload to "satisfy JCS's I-JSON constraints" and only asks (SHOULD) that large integers that cannot round-trip be sent as strings; RFC 7493 §2.2 makes excess precision a SHOULD NOT. M20 decides from that text: the writer is exactly RFC 8785, writes every finite number in its JCS form, and refuses only what JCS cannot write (AMB-94). Validation reports the change of value as `number-inexact` (ADR-005). This ADR fixes the writer, the one number rule, the round-trip laws, the golden vectors and the schema-digest algorithm shared with ADR-009 and ADR-013.

Spec anchors implemented: #signed-payload-and-jws-construction (JCS bytes, I-JSON constraint on what the writer emits; payload member selection is ADR-013), #catalog-entry (`digest`: the JCS bytes of `data`; hashing is ADR-013), #contributor-identity ("MUST be preserved exactly when forwarding"), #consumer-requirements (serialise half of "SHOULD preserve unrecognized members, unchanged"), #top-level-structure (`entries` is "an ordered list", AMB-02).

## Decision

### 1. One writer, one mapping

- `AiCatalog::to_json(&self) -> Json` and `TrustManifest::to_json(&self) -> Json` are the one model → `Json` mapping (crate-private `to_json` on every other model struct, called only from these two). Each defined member present in the model is written under its spec name; `None` is omitted; `Some(vec![])` is written as `[]`, so absent and empty stay distinct (RD-03); `ArtifactSource::Url(s)` is `"url"`, `ArtifactSource::Data(j)` is `"data"`, `Json::Null` included; `additional_signatures: Some(j)` is written as `additionalSignatures` with `j` unchanged, `null` included (excluding it from a payload is ADR-013's job, not this mapping's); `size` is written as a `Json` number of its decimal `u64` digits, so the writer's number rule (§3) decides it like any other number (AMB-97); text members (`tdate` included) are written as the stored string. Every entry of `unrecognized` is written unchanged, except a name the spec defines for that object (AMB-95).
- The mapping never fails; every refusal comes from the writer. `canonical::to_canonical_vec(&AiCatalog) -> Result<Vec<u8>, CanonicalError>` is exactly `catalog.to_json().to_canonical_vec()`. `Json::to_canonical_vec(&self) -> Result<Vec<u8>, CanonicalError>` is the crate-private `canonical::write_canonical`, the only code in the workspace that emits JSON text. `Json` has no `Display` or other text form. Consumers that need JSON text, including the client (ADR-009) and the trust crate (ADR-013), call these two.
- `CanonicalError::NotIJson { pointer: JsonPointer }` is the only error (`#[non_exhaustive]`, `Display`, `std::error::Error`).
- `json::read(&[u8]) -> Result<Json, ParseError>`, ADR-002's one reader, becomes public in this slice with no change: the RFC 8785 vectors and the spec payload example are not catalog documents, and the contract tests use the public API only (ADR-002 §Consequences foresaw this).

### 2. Writer rules (RFC 8785 §3.2)

- No whitespace between tokens (§3.2.1). Output is UTF-8 (§3.2.4). No trailing newline.
- `null`, `true`, `false` as such (§3.2.2.1).
- Strings and member names (§3.2.2.2): U+0008, U+0009, U+000A, U+000C, U+000D as `\b`, `\t`, `\n`, `\f`, `\r`; every other U+0000..U+001F as `\u00hh` with lowercase hex; `"` as `\"`; `\` as `\\`; every other scalar value as its UTF-8 bytes, unchanged (U+007F, U+2028, U+2029 and `/` are not escaped). The decoded string is never altered or normalised (§3.1: "parsed JSON string data MUST NOT be altered"; "MUST preserve Unicode string data 'as is'"). A lone surrogate cannot reach the writer: ADR-002's reader refuses it and `String` cannot hold it (§3.2.2.2 note; AMB-82).
- A string value or member name holding a Unicode noncharacter (U+FDD0..U+FDEF, or a code point whose low 16 bits are FFFE or FFFF), as decided by the crate-private `json::is_noncharacter(char)`, is `NotIJson` (RFC 7493 §2.1: "MUST NOT include code points that identify Surrogates or Noncharacters"; RFC 8785 §3.1 accepts only I-JSON; ADR-002 AMB-93). U+FDCF, U+FDF0, U+FFFD and U+10FFFD are written unchanged.
- Numbers (§3.2.2.3): written as `number::to_canonical(lexeme)` (§3); a lexeme for which it returns `None` (not a finite double) is `NotIJson`. This holds for every `Json` number wherever it sits: `data` (inline nested catalogs included), `extensions`, `additionalSignatures`, unrecognised members and the typed `size`.
- Objects (§3.2.3): members sorted by the UTF-16 code units of their decoded names, compared as unsigned integers, a proper prefix first; recursively, inside arrays too. This is not the `Members` `BTreeMap` order (UTF-8 bytes), which differs once a name holds a code point above U+FFFF and another one in U+E000..U+FFFF. Names are unique by construction (`Members` is a map; ADR-002's reader refuses duplicates).
- Arrays keep element order (§3.2.3: "array element order MUST NOT be changed"), so `entries` order is kept (AMB-02).
- Refusal (AMB-96): the writer walks the value in canonical order and stops at the first defect, so the error and its pointer are deterministic. The pointer is the number or string value; for a member name, the member (object pointer + the name). Nothing is emitted on error, and the input is never changed. A `size` is one more number in that walk (AMB-97).

### 3. The I-JSON number rule (AMB-30, AMB-94)

The crate-private `number` module holds the one number rule (M20):

- `number::to_canonical(lexeme: &str) -> Option<String>`: `x = lexeme.parse::<f64>()` (std, correctly rounded to the nearest double; RFC 8259 number grammar is a subset of what it accepts). If `x` is not finite, `None`. Otherwise `Some(f)`, `f` the ECMAScript `Number::toString(x)` text (ECMA-262 §7.1.12.1 as cited by RFC 8785, including Note 2): `0` for ±0; `-` then the form of `−x` when negative; else, with `s` the `k` shortest round-trip digits and `n` the exponent such that `x = 0.s × 10^n` (from `format!("{:e}", x)`, Rust's shortest round-trip formatting, with the half-even digit ECMA-262 picks on a tie), digits padded with zeros when `k ≤ n ≤ 21`, a decimal point inside them when `0 < n ≤ 21`, `0.` plus `−n` zeros when `−6 < n ≤ 0`, and otherwise `d[.ddd]e±(n−1)`. The writer emits `f`; `None` is `NotIJson`.
- `number::defect(lexeme: &str) -> Option<Defect>` is the predicate `validate` (ADR-005) calls, on `to_canonical`: `Defect::NotIJson` when `to_canonical` is `None` (`number-not-i-json`), `Defect::Inexact` when `f` and `lexeme` denote different exact decimal values (ADR-002 `Number` equality, AMB-88; `number-inexact`), otherwise `None`. The writer and the validator therefore share one rule: the validator's `NotIJson` is exactly the writer's refusal.

So every finite number is written in its JCS form. `1.0`, `1e2`, `1E+2`, `0.1`, `-0`, `1E30`, `100000000000000000000000` are written `1`, `100`, `100`, `0.1`, `0`, `1e+30`, `1e+23` (same value). Written in their JCS form, which denotes another value (`number-inexact`; forms from an independent producer, Node.js `JSON.stringify(JSON.parse(...))`): `9007199254740993` (2^53+1) as `9007199254740992`, `18446744073709551617` (2^64+1) and `18446744073709551615` (2^64−1) as `18446744073709552000`, `9223372036854775808` (2^63, which a double holds exactly) as `9223372036854776000`, `123456789012345678901234567890` as `1.2345678901234568e+29`, `0.1234567890123456789012345` as `0.12345678901234568`, `0.1000000000000000055511151231257827` and `0.10000000000000001` as `0.1`, `295147905179352825856` (2^68 in full) as `295147905179352830000`, `1424953923781206.25` as `1424953923781206.2`, `333333333.33333329` as `333333333.3333333`, `1e-400` and `-1e-400` as `0`. Each form is itself written unchanged. Refused: `1e400`, `-1e400`, `1.8e308` and `-1.8e308`, which overflow to infinity.

Basis (M20, decided by spec under the standing instruction):

- #signed-payload-and-jws-construction: "Canonicalize this payload with JCS [[RFC8785]]" and "The payload MUST satisfy JCS's I-JSON constraints". JCS (RFC 8785 §3.2.2.3) writes every finite double and makes only NaN and Infinity errors; a lexeme that overflows a double has no JCS form. #catalog-entry `digest` hashes "the UTF-8 JCS-canonicalized" `data`.
- "Large integers that cannot round-trip as IEEE 754 doubles SHOULD be encoded as strings" and RFC 7493 §2.2 ("SHOULD NOT include numbers that express greater magnitude or precision than an IEEE 754 double") are SHOULDs, so excess precision is reported (`number-inexact`, a warning) and not refused. RFC 8785's §3.2.2 sample input holds `333333333.33333329` and §3.2.4 writes it `333333333.3333333`; Appendix B note (2) canonicalises `2**68`.
- Refusing such numbers made signatures and digests from RFC 8785-conformant producers unverifiable here, and made the writer a variant of a standard algorithm. That PLAN S2 behaviour is reversed.

Trade-offs, accepted:

- Re-serialising a document changes the value of every inexact number, and `parse(to_canonical_vec(m)) == m` then fails (Law 1's precondition). Validation reports each such number as `number-inexact` at its pointer, so the change is never silent; producers that need the exact value keep it as a string, as the spec recommends.
- A nonzero number below the smallest subnormal (`1e-400`) is written `0`, as an ECMAScript-based JCS producer writes it.

Typed `size` (AMB-97): `Attestation::size: u64` is a ceiling (#attestation-object "An unsigned integer"; #safe-fetching "When `attestation.size` is present, reject responses that exceed it"). It gets no refusal of its own. The mapping writes it as a `Json` number and the rule above writes it like every other number: `0`, `245760`, 2^53 and 2^54 are written unchanged; 2^53+1 is written `9007199254740992`, 2^63 `9223372036854776000` and 2^64−1 `18446744073709552000`, which `parse` then refuses (beyond `u64`). Reasoning:

- The spec requires JCS bytes for a signed manifest and gives no exception for `size`; CDDL `size: uint` cannot follow the SHOULD to encode it as a string. A separate refusal would make a manifest signed by a conformant producer unverifiable, the defect M20 removes, and would bring back a writer variant.
- The ceiling is never lowered where it is applied. The model keeps the exact `u64` read from the source lexeme (ADR-002 AMB-89, the full CDDL `uint` range); a consumer applies #safe-fetching from `Attestation::size`, never from re-serialised bytes.
- What changes is re-serialised output, and only above 2^53 (above 8 PiB). Validation reports it as `number-inexact` at the `size` pointer, and `produce` (ADR-011) returns that report, which the CLI prints, so it is not silent. `number::defect` is the one owner of that check; there is no `size`-specific rule. The same holds for a `size` inside an inline catalog in `data`, where it is a plain `Json` number.

### 4. Laws

For every `m = parse(b)` whose numbers (the typed `size` included) are finite doubles and whose strings hold no noncharacter, `to_canonical_vec(&m)` is `Ok(c)`, and:

1. When no number of `m` is inexact (§3, `number::defect` gives no `Inexact`), `parse(&c) == Ok(m)`: every number is written as a lexeme of the same decimal value, so no value changes. Otherwise `c` holds the JCS form of each inexact number, and validation reports it as `number-inexact`.
2. Whenever `parse(&c)` is `Ok` (it fails only for a typed `size` whose JCS form exceeds `u64`, §3), `to_canonical_vec(&parse(&c)?) == Ok(c)`: every JCS form is a fixed point, so canonicalising twice is byte-identical, and the same input always gives the same bytes.
3. `to_canonical_vec(&m) == m.to_json().to_canonical_vec()`, refusals included.
4. Against the original bytes `b`, never our own output: `to_canonical_vec(&parse(b)?) == ai_catalog_trust::canonicalize(b)`, so a member that `parse` dropped fails the law. Pinned in S7 by `sdk_interop` (ADR-001) for every corpus document, and for every number form by `sdk_interop::numbers_canonicalise_as_ai_catalog_trust_does` (RD-40, closed).

For any other `m` from `parse`, `to_canonical_vec` is `NotIJson` with the pointer of §2. The laws are stated for models from `parse`. A model built in code whose `unrecognized` holds a defined name is covered by AMB-95, not by law 1.

### 6. Schema digest (D17; one algorithm for ADR-003, ADR-009 and ADR-013)

`schema_digest(dir: &Path) -> String` is lowercase-hex sha256 over the concatenation, for every regular file under `dir` (recursively) in ascending byte order of its UTF-8 path relative to `dir` with `/` separators, of: the path, NUL, the file's byte length in decimal ASCII, NUL, the file's bytes. Any entry that is neither a regular file nor a directory makes it panic. Known answers: an empty directory gives `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`; a directory holding `a` = `x` and `b/c` empty gives `4320b59a30ab5a1ab4baec509a15cc2a8919fd31ec8099fc7807a6cffcf50ac6`.

Owner: `crates/turul-ai-catalog/tests/support/schema_digest.rs`, the only definition. Each crate's `tests/schema_digest.rs` includes it with `#[path]` and never copies it; this crate's test scans every `.rs` file under the workspace `crates/` and fails unless exactly one `fn schema_digest(` exists, in the owner (the needle is built at run time so the test does not match itself). Hasher: dev-dependency `sha2 = "0.11"` in `[workspace.dependencies]` (D5, D15), the version ai-catalog-rust 0.4.0 uses, so the dev graph holds one `sha2`. `[dependencies]` stays empty (M6).

Recorded digest of `tests/fixtures/canonical/`: `a24024107f47ecddd78a22c935c52f24ab9a6f5a9f4d637b14d86a6fc860cd0f`, the same value as the constant `RECORDED` in `tests/schema_digest.rs`. Computed by `schema_digest` and independently by a Python implementation of the algorithm above. A change to any golden changes this line, the constant and the revision log together.

New ids (not in PLAN §6): RD-40 and AMB-94 to AMB-97.

- AMB-94: RFC 8785 canonicalises every finite number to its nearest double, its own sample included, and the spec asks only that large integers SHOULD be strings. M20 decides from that text: the writer is exactly RFC 8785 and refuses only a number that is not a finite double (§3). ADR-002's `Number` still compares exact decimal values, so `number::defect` can tell the validator which written numbers change value (`number-inexact`).
- AMB-95: `Members::insert` lets code put `"identifier"` (or an absent optional name such as `"description"`) into a struct's `unrecognized`. Such an entry is not an unrecognised member, and writing it would inject or shadow a defined member, which #consumer-requirements forbids ("An unrecognized member MUST NOT alter how a consumer interprets `identifier`, … or any other defined member"). `to_json` writes a defined name only from its typed field and skips that entry. Trade-off: the skipped entry is lost on serialisation, with no error; `parse` never produces one, and the typed field already gives that member its value, so no model value is changed.
- AMB-96: §2. ADR-002's reader points at the containing object for a lone surrogate in a name because that name cannot be represented; a noncharacter name can be, so the writer points at the member.
- AMB-97: §3 "Typed `size`". The writer's number rule is the one owner: a `size` is written as a `Json` number by the same rule as every other number, with no mapping-level guard, and `number::defect` is the one owner of the `number-inexact` report on it.

## Divergences from ai-catalog-rust 0.4.0

| Id | ai-catalog-rust | This crate | Spec | Pinned by |
|---|---|---|---|---|
| RD-03 | `ai-catalog` serialises with `skip_serializing_if = "Vec::is_empty"` on `tags`, `trust_manifests`, `attestations`, `provenance`, `verification_methods`, so `[]` is dropped | `Option<Vec<_>>`; `[]` is written as `[]` | #consumer-requirements "SHOULD preserve … unchanged" | `canonical_serialisation::empty_and_absent_optional_arrays_round_trip_distinctly`; agreement row in `sdk_interop` (S7) |

RD-40 is closed: it recorded that ai-catalog-trust writes an integer within `i64`/`u64` verbatim, but `serde_jcs` 0.2 writes every integer through `f64`, so both give RFC 8785's bytes for every finite number (§4 law 4). The disagreement was this crate's former refusal, removed by M20.

ai-catalog's document serialiser (`to_string_pretty`) is not JCS. The spec does not require JCS for documents, so this is a design difference (D4), not an RD. `serde_jcs` sorts names by UTF-16 code units, as here.

## Consequences

- One JSON writer in the workspace. The client's JSON output, the trust crate's payloads and `data` digests all reach bytes through `Json::to_canonical_vec`; a second writer, a `Display` for `Json` or a `serde` path is a defect (adr-review check 3).
- A document holding a number that is not a finite double (`1e400`) or a noncharacter parses and validates but cannot be serialised. A number whose JCS form is another decimal value is serialised in that form, as every RFC 8785 producer writes it, and validation warns `number-inexact`; producers keep large or exact numbers as strings, as the spec recommends.
- Plan drift recorded:
  - PLAN §2 lists `json::read` as crate-private; S2 makes it public, as ADR-002 §Consequences foresaw, because the RFC 8785 vectors and the spec payload example are not catalogs.
  - PLAN S2 names no `i_json_strings` test; this ADR adds `tests/i_json_strings.rs`, which ADR-002 AMB-93 assigned to the S2 writer.
  - The schema digest of §6 cannot be computed before the goldens exist; S2 records it in the same slice.
